# Release and container operations

CI runs on pull requests and pushes to `main`; it checks dependencies, builds the application, runs the integration suite against a temporary PostgreSQL database and builds a container image. Production deployment is not automatic.

To prepare a release, update the package version and lockfile, move the relevant changelog entries into that version, review the security and production checklists, and merge to the release commit. Create and push a matching tag such as `v1.0.0`. After CI succeeds, the release workflow builds and publishes `ghcr.io/ardianryan/aversa44` with the version and commit-SHA tags, then creates a GitHub release with generated notes. The repository's Actions permissions must allow package and release publication. Adjust package visibility in GitHub if needed. Tags must match `package.json` and use stable three-part versions. If a tag push did not start the release workflow, run it manually on the default branch with the existing tag as input; verification and image build use that tag.

Build locally with `docker build -t aversa44:local .`. Supply configuration using the deployment environment or an external env file, never bake secrets into the image. Use a dedicated PostgreSQL instance and persist `public/uploads` on writable storage owned by UID 1000. The container runs as the non-root `node` user and exposes port 4400. The application health check depends on its database. Back up database and uploads together and test restoration. See [production operations](PRODUKSI.md) and [security](../SECURITY.md) before launch.

A successful image build or GitHub release does not establish production readiness; payment, webhook delivery, backup restoration and deployment security require verification in the target environment.
